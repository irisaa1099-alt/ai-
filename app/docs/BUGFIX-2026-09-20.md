# 2026-09-20 缺陷修复记录：AI 输出卡住 / 没有输出

本次针对一次全链路只读审查（服务端代理 → `core/llm.js` → 私聊 / 群聊 / 狼人杀界面）发现的
"生成卡住、空回复、完整回复被丢弃"等问题做修复。所有复现与验证都在临时数据目录
（`--data-dir` 指向 `mkdtemp`）中进行，不碰真实 `data/db`，不使用真实模型密钥。

修复前的三条实测结论（本次的靶子）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 上游对 `stream:true` 回**非 SSE 的完整 JSON**（代理模式） | 代理转发 **0 字节**，界面报"模型没有返回任何内容" | 正常拿到全文（1 条用例：`text="半句话，枪口"`） |
| 上游发完内容与 `finish_reason` 但**不发 `[DONE]`、不关连接** | 等空闲看门狗到期 → **抛超时、已生成的完整回复被丢弃** | 直连 0.3 秒收尾、代理 2.5 秒收尾且 `finishReason=stop`、`usage` 完整 |
| 上游**完全不响应**（代理模式） | 客户端 200 秒拿不到任何字节（只能等浏览器看门狗） | **30 秒**返回 HTTP 504 + 中文说明 |

## 服务端代理（`server.mjs` 的 `/api/llm`）

- 新增上游两级超时：**首字节 30 秒**、**流建立后空闲 90 秒**（每收到一块数据重置）。
  这是全项目唯一"服务端自己没有任何兜底"的链路 —— `/api/models` 与 `/api/tts` 早有 15 秒上限。
  首字节超时返回 504 并带上**脱敏后的上游地址**（`safeUpstreamLabel`：Gemini 的 URL 里带 `key=`，
  直接拼进错误消息会把密钥写进界面与日志）。
- 空闲超时**只 cancel 读流、不再 abort 整个请求**：`upstreamAbort` 连着 `res.on('close')`，
  abort 它会连带关掉客户端响应，"上游超时"这帧就送不出去了（实测踩到过）。
- 非 SSE 的 200 响应改为整体读出并翻译成增量帧（新增 `makeTransformer.fromJson` /
  `makeExtractorText` / `contentText`，兼容 OpenAI / Anthropic / Gemini / 本地代理自造格式）；
  用 200 包了 `{"error":…}` 的响应翻译成 error 帧。
- 一个字节都没翻译出来时不再只发 `data: [DONE]`（那会让界面显示"模型没有返回任何内容"），
  改为发一帧明确的中文错误。
- 客户端断开的接线（`upstreamAbort`）提到 `await readBody(req)` **之前**注册：
  Node 16+ 在请求体读完时就会发 `req 'close'`，原来注册在 `readBody` 之后，那两个监听永远收不到事件。
  （当前取消功能靠 `res 'close'` 仍然有效，但不应依赖这种巧合。）

## 流式读取（`core/llm.js`）

- `readSSE` 新增第三种结束条件：`onEvent` 回调返回 `true`（调用方判定"这条流已经说完"）。
  `applyEvent` 在"事件没有正文增量、但带了结束原因"时返回 `true` —— 这正是 OpenAI 系最后一个
  chunk 的形态。以前只认 `[DONE]` 与对端关闭，于是"发完不说再见"的网关会把完整回复拖成超时错误。
- 收到收尾事件后进入**宽限期**而不是立刻断开：代理模式 2.5 秒、直连 300 毫秒。
  分段原因：直连模式客户端根本没请求 `stream_options.include_usage`，finish_reason 之后
  不会再有有用事件，等 2.5 秒纯粹让用户多等；代理模式服务端会转发 `usage`，值得多等一会儿
  （实测：400ms 后到达的 usage 尾包能保住 `prompt=111 / completion=22`）。
  同时清掉本层的空闲看门狗，否则它会按原值先开火，把完整回复判成超时。

## 每次调用的时间上限（原来 7 个生产调用点一个都没传）

不传就落回默认的 **120 秒无内容 / 10 分钟总时限**。现在显式收紧：

| 调用点 | 值 |
| --- | --- |
| `ui/chat.js` 私聊 | 90 秒无内容 / 3 分钟总计 |
| `core/group.js` 群聊每位角色 | 45 秒无内容 / 90 秒总计（一轮串行 N 人，8 人最坏从 80 分钟压到 12 分钟） |
| `core/werewolf.js` 发言与投票 | 60 秒无内容 / 90 秒总计 |
| `core/werewolf.js` 非流式兜底 | 60 秒 / 90 秒 |
| `core/werewolf.js` 自检（用户点按钮在等） | 30 秒 / 45 秒 |
| `core/proactive.js` 主动搭话 | 60 秒 / 2 分钟 |

## 狼人杀（唯一"真的会永久挂起"的链路）

- `askHuman` 增加硬超时 `HUMAN_TIMEOUT_MS = 5 分钟`：界面那边的 resolve 只有"点按钮"与
  "结束整局"两个出口（UI 的 3 分钟计时器只弹提醒、不会替你操作），你切走页面时整局会永久 await。
  超时按"放弃这次操作"处理（弃票 / 跳过 / 放弃开枪），并给出可见告警。
  界面收到该告警时会撤掉操作条，避免留一个永远不会被受理的按钮。
- 投票与 PK 重投的预算检查加上 `!p.isUser`：预算不能拦在真人座位前面 —— 上游只是慢、没挂时，
  前面几个 AI 座位就能耗光预算，轮到你的座位直接 `break`，你从没被问过、票却被算成弃票。
- `ui/werewolf.js` 的 `attach()`（"接着上一局"）补上"同时只允许一局"的守卫，并在替换 session
  之前 `cancelPending()`：否则旧局的引擎会变成孤儿，它 await 的 resolve 随旧 session 被丢弃，
  永久卡死且"结束"按钮救不回来。

## 存储与界面

- `core/store.js` 的 `openDB()`：`onblocked` 不再只 `console.warn`。被其他标签页的旧版本连接挡住时，
  5 秒兜底后 reject 并重置缓存（期间若对方关闭成功则不报假错）。以前 `open()` 会一直挂在 pending，
  而 `idb()` 是 `await openDB()`，于是所有读写永不返回 —— 界面「正在回复…」永久转圈、
  群聊连"正在输入"气泡都不出现，且没有任何报错。对照 `voice/tts.js` 的同名处理（`resolve(null)`）。
- `core/group.js`：群里某个角色缺 API Key 时只跳过 TA，不再 `stop('no-key')` + `break` 整轮
  （实测后果：整轮假模型调用 0 次、其他角色一句话说不出）。只在"本轮名单全部缺 Key"时才报总提示。
- `core/group.js`：停止原因为 `switch`（切会话 / 清空记录 / 删群 / 重绘）时不再落库半句话 ——
  以前"清空群聊记录"后会冒出一条孤零零的旧半句。
- `ui/chat.js`：`generateReply` 的 `finally` 里 `busy` 复位改为**无条件执行**。
  原来它被 `activeGeneration === st` 包住，而 `stopStream()` 会先清空 `activeGeneration`：
  若用户在 `finalizeStream` 的 await 期间点了停止，这段清理会被整段跳过，`busy` 永久为 true，
  发送键一直是"停止"且点它没反应，只能刷新页面。
- `ui/groupchat.js`：`humanize()` 对群聊自造的 `no-key` 提示不再套一层「请求失败：」。

## 侧栏折叠 / 展开时列表弹回顶部

- **现象**：左侧好友栏比视口长时，点分组标题折叠或展开，列表会"啪"地跳回最顶端。
- **根因**：`ui/sidebar.js` 的 `renderList()` 每次都 `mount()` 整块重建 `.side-body`，
  而**被清空的滚动容器 `scrollTop` 必然归零**（实测：先设 `scrollTop=300`，移除全部子节点后立刻变 0，
  把节点原样加回去也回不来）。折叠 / 展开走的就是这条路，所以每次点击都等于"回到列表顶部"。
- **修复**：`renderList()` 前后加「滚动锚点」——
  - `captureScrollAnchor()`：重绘前记下视口内**第一个带 `data-key` 的行**相对容器顶边的偏移
    （好友分组块 `group:<名字>`、好友行 `friend:<id>`、群聊行 `gchat:<id>`、群聊整块 `gchat-section`）；
  - `restoreScrollAnchor()`：重绘后找到同一元素，按它挪动的距离补偿 `scrollTop`；
    锚点行若已不存在（所属分组被折叠 / 被搜索过滤 / 角色被删），退回原来的 `scrollTop` 并夹到新的最大值；
  - 另在下一帧 `requestAnimationFrame` 再校正一次，避免图片头像等"重绘后才定格尺寸"的元素造成二次位移。
- 只改了渲染路径，未改折叠状态存储（仍是 `localStorage` 的 `aichat.groups.collapsed`）与任何数据。

回归守卫：`tools/scrollanchor.mjs`（9 项，假数据 + 无头 Chrome）。它特意做两件事，
否则这条 bug 会被浏览器自身的滚动锚定（Chrome 默认开启）盖住、测不出真实差别：

1. `Network.setBypassServiceWorker` + 注销 SW —— `sw.js` 的 PRECACHE 里有 `ui/sidebar.js`，装过 SW 的
   profile 会一直拿到旧模块，测的就不是磁盘上这一份；
2. 强制 `.side-body { overflow-anchor: none }` —— 位置能不能保住必须只取决于我们自己的实现。

去掉 `renderList()` 末尾的 `restoreScrollAnchor(anchor)` 后重跑，该用例报
「锚点行「group:丁组」抖动了 **310px**」「参照行「group:丁组」抖动了 310px（-10 → -320）」；
加上修复 0px，可反向确认它真的守住了这条路径。
