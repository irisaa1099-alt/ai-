# 2026-09-21 缺陷修复记录：狼人杀顺序发言被"看错时间线"

本次只修一条用户直接看到的问题：**白天是按座位顺序依次发言，但前置位的角色会去质问
"后面的人怎么不说话"** —— 后置位那一刻根本还没轮到开口。

## 现象（线上原文，8 号发言，第 1 天）

```
（8 号 程栖 发言）
我是 8 号，平民一个，没什么牌好亮的……
先说 1 号吧——首夜就跳预言家，报的还是 9 号好人。这位听众，你这查得也太干净了，干净到像没查过。
不过我不急着踩他。我更想看看 9 号 Iris 怎么接——被人捞了一整轮还不出声，这反倒比 1 号更值得记一笔。
```

9 号排在 8 号**后面**，此刻还没轮到它。这句"被人捞了一整轮还不出声"把"还没轮到"读成了
"一直躲着不说话"，而这个"疑点"在顺序发言的规则里根本不存在 —— 它会被后面的角色当成
真实线索接着讨论（"9 号确实很安静"），一路污染整局的推理。

## 根因

给发言人的提示词（`dayPromptFor()`）里，跟"谁说过话"有关的信息只有两段：

- `存活玩家：1 号 林晚、2 号 …` —— 只有名单；
- `【已经公开发生的事】`（`publicLogText(s, 40)`）—— 只有**已经说过什么**。

**没有任何一处告诉它"现在轮到谁、你是第几位"**。模型只好从"公开记录里没有 9 号的声音"倒推，
得出"9 号一直不吭声"。方向是对的（缺信息），结论是错的（时间线看反了）。

## 修法（三层，与"狼人认狼"那套兜底同构）

### ① 提示词讲清时间线（主防线）

`core/werewolf.js` 新增两个纯函数，由 `dayPromptFor()` 拼在公开记录与【发言要求】之间：

- `speakOrderFor(state, me, opts)`：本轮顺序（普通发言＝存活玩家按座位升序，PK 发言＝平票座位升序）、
  我的下标、**已经发过言的是谁**、**还没轮到的是谁**；
- `speakOrderNote(...)`：把上面的结论写成【发言顺序（重要）】那一段，并明写两条禁止项 ——
  不要催还没轮到的人发言，也不要把"不吭声 / 一直不出声 / 被人捞了还不表态 / 怎么不接话"当疑点；
  想听后面的人表态可以说"等 X 号表态"，但不算疑点。
  【发言要求】里再补一条短提醒。

要点：

- 顺序与引擎的循环**同源**，不在提示词里另算一套（普通发言＝`phaseDay()` 的循环顺序，
  PK 发言＝`phaseVote()` 的 `pkSeats`）。
- **PK 的"已经说过"只能来自 PK 自己那一轮**：`phaseVote()` 里新增局部数组 `pkSpoken`，
  随 PK 循环增长并传给 `speakTurn()`。原来若读 `state.spokenSeats`，PK 时全场都已经说过话，
  那段会写成"在你之前全体都发过言了"，等于把顺序信息又抹掉。
- 没有权威"谁已经说过"的记录时（直接拼提示词的调用方、老存档），按顺序发言的**常态**推断
  （前面的人说过了、后面的还没轮到），而不是写成"你是第一个发言的人"这种假话。
- 这一段全是**公开信息**（座位、名字、顺序），不进 `state.log`、不碰任何身份 —— 与 5.9 的信息边界不冲突。

### ② 检测 + 纠正重说

`looksLikeSilenceUrge(text, state, me, opts)` 只在"**点名了还没轮到的座位**（座位号或名字）
**且**出现沉默/催促用词"时判真；句子里带"昨天 / 上一轮 / 第 N 天"这类时间标记时一律放过 ——
"5 号昨天一整轮都没怎么说话"是**对过去几轮的正常复盘**，不能误伤（宁可少判，与
`looksLikeSellingTeammate` 同一个取舍）。

命中后 `guardSilenceUrge()` 点名纠正、让模型重说一次（纠正段里直接点名"还没轮到的是谁"），
与 `guardWolfSpeech()` 的位置、写法一致（重说不带 `live`，流式临时气泡照旧由落库消息替换）。

### ③ 删句兜底

重说还犯就把那一句删掉（`stripSilenceUrge()`，投票行单独保留）；整段都在催才换成一句
不违规的场面话。**人类玩家不受任何限制** —— 你想催谁、怎么演都是你的自由。

## 回归守

`tools/selftest.mjs` 5.7 新增三条用例：

1. **顺序说明的措辞**：8 号发言时必须是"你是第 8 位"、已发过言的是 1~7 号、还没轮到的是 9 号；
   第一个/最后一个发言人的边界措辞；PK 分支（顺序＝平票座位、已说过的人来自 PK 记录）；
   以及白天提示词里真的带着这一段。
2. **检测与删句的不误伤边界**：线上那句必判真；已发过言的人被点评"沉默"、带时间标记的复盘、
   "我先听听 9 号怎么说"都不判；删句只删催人那句，正常内容与投票行保留。
3. **引擎层三步**：模型第一次就催人 → 纠正重说且采用重说版（投票行照常解析）；
   重说还在催 → 句子被清掉、**票不丢**（换成场面话时把投票行接在后面）；人类玩家不被改写；
   PK 发言的提示词里也带顺序说明。

`tools/werewolfcheck.mjs` 新增 **Z 条**（真浏览器 + 假模型）：假模型开 `/urge` 模式后，
照着提示词里"还没轮到的"那一位**故意**写"X 号到现在一直不吭声，我看有问题"，
断言 ① 每一次发言提问都带【发言顺序（重要）】/「你是第 N 位」/「身后的人还没轮到」；
② 引擎的 `guardSilenceUrge` 真的触发过（否则这条检查没测到东西）；
③ 群里 0 条"催沉默"的发言；④ 兜底记录只进 `debug`，不进公开记录。

## 本次验证结果

| 命令 | 结果 |
| --- | --- |
| `node tools/selftest.mjs` | 154 通过 / 0 失败（新增 3 条） |
| `node tools/werewolfcheck.mjs` | 32 通过 / 0 失败（新增 Z 条：假模型故意催后置位 8 次，引擎拦下 4 次，13 条发言里"催沉默"0 条） |

## 影响面（狼人杀顺序发言）

- 只有提示词与发言兜底变了，**引擎的规则与流程没动**：座位、发言循环、投票、PK、胜负判定都与之前一致。
- 发言的 LLM 调用次数只在"模型写了催人句"时多一次（重说），正常发言仍是一次调用。
- `state.log` / 群消息 / HUD 的公开面没有新增任何字段（顺序说明只进提示词；兜底记录只进 `debug`）。
- **遗言不在这条兜底的范围内**（`lastWordsPromptFor` 不带顺序说明、也不过 `guardSilenceUrge`）：
  遗言是在"天亮公布死讯"与"被票出结算"这两个时刻说的，与"本轮按座位顺序发言"无关，
  而它自己的提示词也只让当事人谈自己那点事（聊身份、查验、狼坑、死因是谜）。
  若日后发现遗言里也冒出这类句子，再接同一条兜底即可（判据与接口都是现成的）。

# 同日第二处：建群 / 拉人时，勾选一个角色会把成员列表弹回最顶部

本次只修一条用户直接看到的问题：**新建群聊（或群聊里的「＋拉人」）时，成员列表滚到下面去找角色，
点一下勾选，列表立刻跳回最上面**，接着选人就得重新滚回去。

## 现象

弹层第二块「② 拉谁进群」里的好友列表（`.ge-member-list`，`max-height:240` + `overflow-y:auto`）
本来就比视口长，好友多的时候要滚着找。勾一个角色 → 列表弹回顶部。

## 根因

与 09-20 那条「侧栏折叠时列表弹回顶部」**同根**（见 `BUGFIX-2026-09-20.md`）：
`ui/groupeditor.js` 的 `memberPicker()` 里，行点击走的是「改选中集合 → **重建整张列表**」，
而**被清空的滚动容器 `scrollTop` 会被夹到 0**，重建之后自然停在最上方。

比侧栏那条更刁钻的地方在于**触发条件**（这一点是先量出来才敢下手的）：

- 用无头 Chrome 穷举「滚动位置 × 弹层主体位置 × 点击目标 × 好友数量 × 视口高度」10 个场景后，
  只有**列表已经滚到底部**时才会真的丢位置：`scrollTop 658 → 0`，并且冒出一条真的 scroll 事件（用户看得见）；
- 滚在**中段**（`scrollTop=120`）时反而不丢 —— Chrome 里「清空 + 同步重建」之间没有布局，
  浏览器还没来得及把滚动位置夹下去，内容就补回来了。

所以这条 bug 用「随便滚一下再点」的姿势是测不出来的：**必须滚到底再点**（而"找靠后的角色"恰恰是滚到底）。

## 修法（`ui/groupeditor.js` 的 `memberPicker()`）

1. **勾选 / 取消勾选就地更新那一行**（`class` + 勾选图标），不再重建列表 ——
   滚动位置不再受影响，顺带把**键盘焦点**也保住了（旧代码重建后连焦点一起吃掉，
   `activeElement` 掉回 `<body>`，连续勾选只能重新 Tab 过去）；
2. 确实需要重建时（点 chip 的 × 取消选中）用 `renderList({ keepScroll: true })`，
   重建后**显式**把 `scrollTop` 放回去；
3. 只有搜索词变化才回到顶部，而且同样是**显式赋值** `scrollTop = 0`：
   不再依赖「清空会归零」这种浏览器实现差异（实测 Chrome 里那条搜索路径并不会归零，
   Firefox / Safari 会 —— 显式赋值让三边表现一致）。

只改了渲染路径：选中集合、保存逻辑、群成员数据都没动。

## 回归守

`tools/scrollanchor.mjs` 新增 **6 条**（第 5 节，假数据 + 无头 Chrome），姿势就是「滚到底 + 真实鼠标点击」：

1. 成员列表可滚动，且测试期间强制 `.ge-member-list{overflow-anchor:none}` —— 位置能不能保住
   必须只取决于我们自己的实现，不能算浏览器原生锚定的功劳；
2. **根因复核**：另造一个同款容器，滚到中段 / 底部后清空子节点，断言 `scrollTop` 归零
   （把"为什么必须就地更新"量成事实，也防止日后有人把这条 bug 的根因判断改错）；
3. 滚到底 → 真实鼠标点击（`Input.dispatchMouseEvent`，只有真实点击才会把焦点交给那一行）→
   断言 `scrollTop` 不变、**0 次 scroll 事件**、选中 +1、chip +1、焦点仍留在 `.ge-member`；
4. 滚到底后连续勾选 / 取消勾选 4 次，位置始终不动；
5. 滚到底后点 chip 的 × 取消选中（走"不得已才重建"的那条分支），位置同样不动；
6. 搜索是唯一允许回到顶部的入口（结果集变了），且断言此时列表仍比视口长 ——
   排除"内容变短被夹回顶部"这种假通过。

反向确认（把 `ui/groupeditor.js` 换回旧实现后重跑同一份用例）：

```
✗ 滚到列表底部，真实点击勾选一位角色：不回顶、焦点还在这一行
    滚到底时点「甲组1」，列表从 658 跳到了 0（回到了最上方）
```

换回修复版本后该用例通过（`scrollTop 保持 658，0 次滚动，焦点留在 .ge-member`）。

## 版本与验证

- `sw.js` 缓存版本 `aichat-v53` → `aichat-v54`：改的是 `ui/groupeditor.js`，而它在 PRECACHE 清单里，
  不升版本的话已装过 Service Worker 的页面第一次刷新拿到的还是旧模块。

在独立临时数据目录中运行：

| 命令 | 结果 |
| --- | --- |
| `node tools/scrollanchor.mjs` | 15 通过 / 0 失败（新增 6 条，全部集中在第 5 节） |
| `node tools/groupcheck.mjs` | 20 通过 / 0 失败（含"拉人弹层里取消一位成员"这条真实界面路径） |
| `node tools/selftest.mjs` | 154 通过 / 0 失败 |
| `node tools/audit.mjs` | 阻断 0、警告 0 |

## 影响面（建群成员列表）

- 只动 `memberPicker()` 的渲染路径：选中集合、`saveGroup` / `setGroupMembers`、群成员数据与落盘全都没变。
- 行为上只有两处与旧版不同，且都是本次要的结果：
  ① 勾选 / 取消勾选不再让列表跳动、也不再丢焦点；
  ② 搜索时**稳定**回到列表顶部（旧版在 Chrome 里会保留原位、在 Firefox / Safari 会回到顶部，本就不一致）。
